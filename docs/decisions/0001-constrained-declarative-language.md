# ADR-0001: Adopt a Constrained Declarative Topology Language

## Status

Proposed

## Date

2026-09-02

## Context

Stack needs a source format for software architecture and technology-stack diagrams. The format will be authored by humans, generated by language models, reviewed in Git, and consumed by more than one renderer or editor over time.

The central product promise is consistently polished output. A language that exposes coordinates, arbitrary styling, embedded assets, or renderer-specific commands would make that promise dependent on every author. A highly permissive graph language would also create many equivalent ways to express the same diagram, reducing generation reliability and making compatibility harder to preserve.

At the same time, a format that infers every relationship from prose would be ambiguous and difficult to validate. The language needs explicit topology, containment, direction, and a small amount of architectural meaning.

## Decision

Stack will use a versioned, declarative, text-based DSL with four primary constructs:

- nodes for architectural entities;
- groups for containment boundaries;
- edges for relationships between nodes;
- layout blocks for a small set of constraints and hints.

The language will describe semantics rather than drawing instructions. It will not expose coordinates, dimensions, arbitrary colors, fonts, CSS, SVG, ports, edge paths, scripting, imports, macros, or network assets. A diagram may select a symbolic catalog-managed theme, but source cannot define theme values or per-element overrides.

Stack 1.0 will use one global identifier namespace and exactly one diagram per file. Edges will connect nodes only. Group containment and same-rank declarations will be constraints; direction and relative order will be hints. Renderers will own all remaining composition and visual-system decisions.

The language will have explicit version declarations, strict unknown-syntax handling, structured diagnostics, bounded diagram complexity, and graceful fallback for unavailable theme-owned icons and themes.

Theme and icon ownership is refined by [ADR-0002](./0002-theme-owned-icons.md).

## Alternatives Considered

### Adopt Mermaid syntax as-is

- Pros: Familiar to many users; broad diagram coverage; existing ecosystem.
- Cons: Supports many diagram types and syntax forms that do not align with Stack's narrow visual-quality contract; compatibility would depend on an external language.
- Rejected: Stack needs its own constrained semantics and evolution policy.

### Use JSON or YAML

- Pros: Existing parsers and schema tooling; easy machine interchange.
- Cons: More punctuation or indentation ceremony; graph relationships become verbose; YAML has multiple surprising scalar forms and implicit typing.
- Rejected: A small dedicated grammar is easier to read, generate, validate, and format consistently.

### Expose coordinates and visual styles

- Pros: Authors can reproduce a precise composition and cover unusual cases.
- Cons: Moves visual quality responsibility into source, produces fragile diffs, prevents responsive reflow, and creates renderer-specific behavior.
- Rejected: Conflicts with Stack's primary product promise.

### Infer all layout with no hints

- Pros: Smallest possible language; maximum renderer control.
- Cons: Authors cannot communicate meaningful reading direction, peer alignment, or order when topology alone is insufficient.
- Rejected: A limited vocabulary of scoped hints provides intent without becoming a drawing language.

### Permit arbitrary icon URLs or embedded SVG

- Pros: Unlimited icon coverage and exact brand artwork.
- Cons: Introduces security, availability, licensing, caching, and style-consistency problems.
- Rejected: Stack uses safe symbolic icon identifiers resolved from the selected theme in the canonical catalog.

### Permit inline colors, fonts, or theme objects

- Pros: Authors can reproduce brand systems without installing renderer resources.
- Cons: Creates an unbounded styling language, weakens renderer quality guarantees, and makes source dependent on visual implementation details.
- Rejected: Source selects one trusted theme by identifier; the theme catalog owns its visual tokens.

### Allow edges to connect groups

- Pros: Convenient for high-level diagrams and reduces explicit gateway nodes.
- Cons: Makes the real endpoint ambiguous, complicates routing and nesting semantics, and can conceal important architectural boundaries.
- Rejected for 1.0: Authors connect the specific participating node.

## Consequences

- Source remains concise, reviewable, and suitable for language-model generation.
- Renderers have enough control to maintain a coherent visual system and responsive composition.
- Some diagrams will require authors to split a large system into multiple views.
- Authors cannot manually repair a poor automatic layout with coordinates; renderer quality and the small layout vocabulary must be sufficient.
- Icon coverage belongs to the selected theme, and unresolved icons degrade safely to semantic kind fallbacks.
- Theme selection can express a visual context without exposing arbitrary styling; unavailable custom themes degrade safely to the core `default` theme.
- Strict parsing and version checks prevent plausible-looking output that silently omits unknown meaning.
- Language changes must begin in this specification repository before implementation repositories adopt them.
